# 보안 모델

이 문서는 AI Company가 Skynet 프로토콜 상의 서브넷 구현으로서, 아키텍처 레벨에서 보안 메커니즘을 보충하는 방법을 설명합니다.

## 개요

### 계층별 책임 분담

| 계층 | 책임 내용 | 설명 |
|------|---------|------|
| **Skynet 프로토콜 레이어** | 네트워크 통신, 기초 암호학 프리미티브, 서브넷 추상화 | 경량화, 유연, 범용 |
| **서브넷 구현 레이어 (AI Company)** | 특정 시나리오의 보안 메커니즘, 클라이언트 구현 가이드 | 서브넷 유형에 따라 필요에 따라 구현 |

Skynet 프로토콜은 **최소 필요**한 보안 메커니즘만 정의하여 경량화와 유연성을 유지합니다. 특정 서브넷(예: AI Company)은 자체 요구에 따라 아키텍처 레벨에서 추가 보안 조치를 보충합니다.

---

## 1. 메타데이터 보호

### Skynet 프로토콜 레이어 포지셔닝
Skynet 프로토콜은 **메타데이터 보호를 제공하지 않으며**, 프로토콜 경량화를 유지합니다.

### AI Company 서브넷 레이어에서 구현

기업급 애플리케이션의 경우, 메타데이터 보호 방안은 AI Company가 설계하고 구현합니다:

#### 기본 조치 (권장)
| 조치 | 설명 |
|------|------|
| **라우팅 무작위화** | 클라이언트가 서비스 노드를 무작위로 선택 |
| **타임스탬프 정밀도 낮춤** | 초 단위 정밀도 (밀리초 아님) |

#### 장기 계획: 혼합 네트워크
강력한 메타데이터 보호가 필요한 경우, AI Company는 향후 버전에서 혼합 네트워크(예: Loopix)를 도입할 수 있지만, 다음이 필요합니다:
- 상당한 아키텍처 변경
- 더 높은 지연 시간과 대역폭 오버헤드 수용
- 개인정보 요구가 매우 높은 시나리오에만 적용

## 2. 양자 내성 암호학 (PQC) 이행

### Skynet 프로토콜 레이어 포지셔닝
Skynet 프로토콜은 **확장점을 예약**하여 PQC 알고리즘 이행을 지원하지만, 강제하지 않습니다.

### AI Company 서브넷 레이어에서 구현

#### 2.1 혼합 인증서 모드
AI Company는 고전 암호학과 포스트 퀀텀 암호학을 동시에 지원하는 구현을 책임집니다:
- **이중 키 쌍**: 각 신원은 Ed25519와 CRYSTALS-Dilithium 키 쌍을 동시에 보유
- **이중 서명**: 중요한 작업은 두 알고리즘을 동시에 사용하여 서명
- **점진적 이행**: 먼저 검증을 지원한 다음 점진적으로 PQC 중심으로 전환

#### 2.2 PQC 암호 스위트
| 컴포넌트 | 고전 알고리즘 | PQC 알고리즘 | 혼합 모드 |
|------|---------|---------|---------|
| **서명** | Ed25519 | CRYSTALS-Dilithium | Ed25519 + Dilithium |
| **키 캡슐화** | X25519 | CRYSTALS-Kyber | X25519 + Kyber |
| **해시** | Blake3 | Blake3 | Blake3 |

#### 2.3 키 회전 전략
- **긴급 회전**: 양자 위협 발견 시 즉시 전체 네트워크 키 회전 트리거
- **정기 회전**: 기본적으로 90일마다 장기 키를 한 번 회전
- **전방 보안**: 세션 키에 PQC KEM을 사용하여 전방 보안 보장

### 이행 로드맵
```
단계 1 (현재): 고전 암호학 중심
    ↓
단계 2: 혼합 모드 (고전과 PQC 동시 지원)
    ↓
단계 3: PQC 중심, 고전은 대안으로
    ↓
단계 4: 완전 PQC (고전 알고리즘 지원 제거)
```

## 3. 클라이언트 보안 구현 가이드 (AI Company 서브넷 레이어)

### Skynet 프로토콜 레이어 포지셔닝
Skynet 프로토콜은 **인터페이스를 정의**하지만, 구체적인 구현은 클라이언트와 서브넷 레이어에 맡깁니다.

### AI Company 서브넷 레이어 사양

#### 3.1 키 관리 사양

##### 키 저장 계층
| 키 유형 | 저장 위치 | 암호화 보호 |
|---------|---------|---------|
| **신원 개인 키** | 시스템 키체인 / HSM / TEE | 하드웨어 레벨 보호 |
| **장치 개인 키** | 암호화된 로컬 스토리지 | 사용자 비밀번호 파생 키 |
| **세션 키** | 메모리 (프로세스 격리) | 자동 소멸 |

##### 키 파생 요구 사항
- **알고리즘**: Argon2id 강제 사용
- **파라미터**:
  - 메모리: 최소 64MB
  - 반복 횟수: 최소 3회
  - 병렬도: 4
  - 솔트: 16바이트 CSPRNG 생성

##### 키 백업 및 복구
- **Shamir 비밀 공유**: 복구 키를 5개로 나누고, 3개로 복구 가능
- **오프라인 저장**: 사용자가 복구 키를 인쇄하거나 오프라인 장치에 저장하도록 권장
- **소셜 복구**: 선택적으로 신뢰할 수 있는 연락처의 도움을 받아 복구 지원

#### 3.2 API Key 관리 사양 (AI Company 특정)

##### API Key 보안 원칙
| 원칙 | 설명 |
|------|------|
| **최소 권한** | 각 API Key는 작업 완료에 필요한 최소 권한만 부여 |
| **단기 유효** | 영구 API Key보다 단기 Token 우선 사용 |
| **격리 사용** | 다른 Agent/서비스는 다른 API Key 사용 |
| **취소 가능** | 유출되거나 더 이상 필요하지 않은 API Key는 언제든지 취소 가능 |

##### API Key 저장
- **저장 위치**: 시스템 키체인 / 보안 키 관리 서비스 (KMS)
- **암호화 보호**: 정적 암호화, 마스터 키로 API Key 암호화
- **메모리 보호**: 사용 후 즉시 메모리에서 제거, 디스크로 교환 방지

##### API Key 수명 주기 관리
```
생성 → 배포 → 사용 → 회전 → 취소 → 소멸
```

**생성**:
- CSPRNG을 사용하여 충분한 강도의 API Key 생성 (최소 256비트 엔트로피)
- 생성 시간, 생성자, 용도, 권한 범위 기록

**배포**:
- 보안 채널 전송 (종단 간 암호화)
- 로그, 오류 메시지에서 완전한 API Key 노출 피하기
- 식별용으로 Key의 앞/뒤 몇 자리만 표시

**사용**:
- 환경 변수 또는 보안 설정 파일로 주입, 하드코딩하지 않음
- 요청 헤더 또는 권한 필드로 전달 (예: `Authorization: Bearer <key>`)
- URL 쿼리 파라미터로 전달 피하기

**회전**:
- 정기 회전 (기본 90일)
- 새/이전 Key 공존 과도기 지원 (최소 7일)
- 보안 이벤트 트리거 시 즉시 회전

**취소**:
- 셀프 취소 인터페이스 제공
- 취소 후 즉시 무효화
- 취소 이유와 시간 기록

**소멸**:
- 모든 저장 위치에서 삭제
- 메모리와 디스크의 잔여물 덮어쓰기
- 소멸 완료 확인

##### API Key 유출 응급 대응
1. **즉시 취소**: 유출 발견 후 즉시 취소
2. **감사 로그**: 해당 Key의 모든 사용 기록 확인
3. **영향 평가**: 유출로 인한 손실 평가
4. **사용자 알림**: 영향을 받는 사용자/팀 알림
5. **근본 원인 분석**: 유출 원인 찾아 재발 방지
6. **보안 강화**: 저장 및 사용 방식 개선

##### 임시 Token 우선
Agent 시나리오의 경우, 영구 API Key보다 단기 Token 우선 사용:
- **OAuth 2.0**: Client Credentials 또는 Authorization Code Flow 사용
- **JWT**: 단기 JWT Token (유효 기간 < 1시간)
- **동적 새로고침**: Refresh Token으로 새로운 Access Token 획득

#### 3.3 난수 생성 사양

##### 엔트로피 소스 요구 사항
- **주요 엔트로피 소스**: 운영 체제 CSPRNG (Windows: `CryptGenRandom`, Linux: `/dev/urandom`)
- **보충 엔트로피 소스**:
  - 장치 센서 데이터 (가속도계, 자이로스코프)
  - 사용자 상호작용 타임스탬프
  - 네트워크 지연 시간 측정
- **엔트로피 혼합**: Fortuna 또는 Yarrow 알고리즘으로 다중 소스 엔트로피 혼합

##### CSPRNG 검증
- NIST SP 800-90A 표준 구현
- 정기적으로 무작위성 테스트 수행 (Dieharder, TestU01)
- 암호학적으로 안전하지 않은 난수 생성기 사용 금지

#### 3.4 참조 구현 (AI Company 서브넷 SDK)
공식 SDK 제공, 다음을 포함:
- **암호 라이브러리 래핑**: 통합된 암호학 프리미티브 인터페이스
- **키 관리 모듈**: 즉시 사용 가능한 보안 키 저장
- **API Key 관리 모듈**: 안전한 API Key 수명 주기 관리

## 4. 보안 감사 및 로그 (AI Company 책임)

### Skynet 프로토콜 레이어 포지셔닝
감사 로그는 **Skynet 프로토콜에 포함되지 않으며**, 완전히 서브넷 생성자가 요구에 따라 자율적으로 구현합니다.

### 이유
다른 서브넷 유형의 감사 요구 사항은 매우 다릅니다:

| 서브넷 유형 | 감사 요구 사항 | 예시 |
|---------|---------|------|
| **조직 서브넷 (AI Company)** | 높은 요구 사항 | 완전한 감사 로그, 불변성, 다년 보존, 규정 준수 인증 |
| **커뮤니티 서브넷** | 중간 요구 사항 | 기본 작업 로그, 선택적 보존 |
| **개인 서브넷** | 낮은 요구 사항 | 감사 로그가 전혀 필요하지 않을 수 있음 |

### AI Company 서브넷에서 구현

AI Company는 기업급 서브넷으로서, 완전한 감사 로그 기능 구현을 책임집니다:

#### 4.1 감사 이벤트 유형
- 신원 인증 이벤트
- 키/API Key 작업
- 권한 변경
- 민감한 리소스 액세스

#### 4.2 로그 보안 요구 사항
- **클라이언트 로컬 저장**: 감사 로그는 클라이언트가 수집하고 저장
- **암호화 보호**: 민감한 감사 로그는 암호화 저장
- **무결성 보호**: 디지털 서명으로 조작 방지
- **서브넷 레벨 구성**: 서브넷 생성자가 감사 정책 정의 가능

## 5. 시빌 어택 방어 (AI Company 책임)

### Skynet 프로토콜 레이어 포지셔닝
Skynet 프로토콜은 **시빌 어택 방어를 강제하지 않으며**, 프로토콜 유연성을 유지합니다.

### AI Company 서브넷 레이어에서 구현

#### 5.1 다층 방어 시스템

| 방어 계층 | 메커니즘 | 설명 |
|---------|------|------|
| **1층** | 신원 인증 | 이메일, 휴대폰 번호, WebAuthn 등 |
| **2층** | 작업 증명 | Hashcash 또는 유사 메커니즘 |
| **3층** | 소셜 그래프 검증 | 신뢰할 수 있는 연락처 보증 |
| **4층** | 경제적 담보 | Token을 보증금으로 잠금 |

#### 5.2 신원 인증 옵션
- **WebAuthn/FIDO2**: 권장되는 강력한 인증 방식
- **이메일 인증**: 인증 링크 전송
- **휴대폰 번호 인증**: SMS 인증 코드
- **OAuth**: 타사 신원 제공자 지원 (Google, GitHub 등)

#### 5.3 신용 시스템
- **초기 신용**: 신규 사용자는 신용이 낮고 작업 빈도 제한
- **신용 축적**: 정상 사용으로 점진적으로 신용 향상
- **신용 페널티**: 악의적인 행동은 신용 저하
- **서브넷 간 신용**: 신용은 다른 서브넷 간에 공유 가능

## 6. 전방 보안 강화 (서브넷 레이어 구현 가이드)

### Skynet 프로토콜 레이어 포지셔닝
Skynet 프로토콜은 **Double Ratchet과 MLS를 사용**하여 전방 보안을 제공하지만, 구체적인 구현 세부 사항은 클라이언트가 책임집니다.

### AI Company 서브넷 레이어 사양

#### 6.1 키 소멸 사양

##### 메모리 키 소멸
- **제로 덮어쓰기**: memset_s 또는 동등한 함수로 키 메모리 덮어쓰기
- **여러 번 덮어쓰기**: 최소 3회 다른 패턴으로 덮어쓰기
- **메모리 잠금**: mlock/VirtualLock으로 키가 디스크로 교환되는 것 방지

##### 영구 키 소멸
- **보안 삭제**: shred 또는 동등한 도구 사용
- **SSD 처리**: SSD에 특화된 처리 (TRIM, 보안 삭제)
- **소멸 확인**: 키 자료가 복구 불가능함을 확인

#### 6.2 전방 보안 보장
- **세션 키 수명 짧음**: 각 메시지마다 키 회전 (Double Ratchet)
- **키 캐시 없음**: 오래된 메시지 해독에 사용할 수 있는 키는 캐시하지 않음
- **완전 전방 보안 (PFS)**: PFS 속성 명확히 보장

## 7. 보안 경계 및 심층 방어 (AI Company 서브넷 레이어)

### 7.1 보안 경계 정의

| 경계 | 보호 조치 |
|------|---------|
| **클라이언트 경계** | 샌드박스 격리, 프로세스 격리, 메모리 보호 |
| **네트워크 경계** | TLS 1.3, 인증서 잠금, 인증서 투명성 |
| **서비스 노드 경계** | 최소 권한, 네트워크 격리, 침입 탐지 |
| **데이터 경계** | 종단 간 암호화, 정적 암호화, 액세스 제어 |

### 7.2 심층 방어 전략

```
1층: 클라이언트 보안
    ↓
2층: 전송 보안 (TLS 1.3 + Noise)
    ↓
3층: 종단 간 암호화 (X3DH + Double Ratchet / MLS)
    ↓
4층: 다중 노드 검증
    ↓
5층: 감사 로그 및 이상 탐지 (선택적)
```

## 8. 보안 규정 준수 및 인증 (AI Company 서브넷 레이어)

### 8.1 규정 준수 표준 (필요에 따라 충족)
- **GDPR**: 데이터 보호, 사용자 제어권, 이식성
- **HIPAA** (적용 가능한 경우): 의료 데이터 보호
- **SOC 2**: 보안, 가용성, 기밀성
- **ISO 27001**: 정보 보안 관리 시스템

### 8.2 보안 인증 (선택적)
- **타사 감사**: 정기적으로 독립적인 보안 감사 수행
- **취약점 현상금**: 취약점 현상금 프로그램 수립
- **공개 투명성**: 보안 감사 보고서 공개

### AI Company 보안 모델 보충

Skynet 상의 기업급 서브넷 구현으로서, AI Company 보안 모델은 다음을 통해 프로토콜 레이어를 보충합니다:

1. **메타데이터 보호**: AI Company가 구현 책임, 기본 조치와 장기 계획 제공
2. **양자 내성 이행**: AI Company가 구현 책임, 혼합 인증서 모드, 점진적 이행 로드맵
3. **클라이언트 보안**: 키 관리 사양, API Key 관리 사양, 난수 생성 사양, 공식 SDK
4. **감사 로그**: AI Company가 구현 책임, 완전한 감사 로그 기능
5. **시빌 방어**: AI Company가 구현 책임, 다층 방어, 신원 인증, 신용 시스템
6. **전방 보안**: 키 소멸 사양, PFS 보장
7. **규정 준수 인증**: GDPR, SOC 2, ISO 27001

둘을 결합하여 완전한 기업급 보안 시스템을 구성하는 동시에, Skynet 프로토콜 자체의 경량화와 유연성을 유지합니다.
