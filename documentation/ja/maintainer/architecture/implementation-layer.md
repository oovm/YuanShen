# 実装レイヤー（augur-* コアモジュール）

本ドキュメントでは、AI Company システムにおける実装レイヤーの各コアモジュールを詳細に説明します。実装レイヤーはプレゼンテーションレイヤーとプロトコルレイヤーの間に位置し、コアビジネスロジックと機能実装を提供します。

## 概要

実装レイヤーは複数の独立した `augur-*` モジュールで構成され、各モジュールは特定の機能領域を担当します。これらのモジュールは依存性注入と明確なインターフェース設計を通じて連携し、上位アプリケーションに堅牢な機能基盤を提供します。

## モジュールリスト

実装レイヤーには以下のコアモジュールが含まれます：

| モジュール名 | 責任 | 状態 |
|---------|------|------|
| [augur-agent](#augur-agent) | エージェント管理 | コア |
| [augur-orchestrator](#augur-orchestrator) | タスクオーケストレーションとワークフロー管理 | コア |
| [augur-organization](#augur-organization) | 組織、部門、ロール管理 | コア |
| [augur-skill](#augur-skill) | スキルプラグインと能力拡張 | コア |
| [augur-memory](#augur-memory) | メモリシステム管理 | コア |
| [augur-persistence](#augur-persistence) | 永続化レイヤー実装 | インフラストラクチャ |
| [augur-file-system](#augur-file-system) | ファイルストレージサービス | インフラストラクチャ |
| [augur-types](#augur-types) | 型定義とエラー処理 | インフラストラクチャ |

## モジュール詳細説明

### augur-types

**責任：** 実装レイヤーの共有型定義と統一されたエラー処理メカニズムを提供します。

**主な機能：**
- コアデータ構造の定義（ワークスペース、プロジェクト、会社、チーム、従業員、スキルなど）
- 統一エラー型 `AugurError` とエラー処理メカニズム
- 標準の列挙型の提供（`ProjectStatus`、`RoleType`、`SkillLevel` など）
- 国際化されたエラーメッセージのサポート（i18n キーを通じて）

**コア構造体：**
- `Workspace` - ワークスペース
- `Project` - プロジェクト
- `Company` - 会社
- `Team` - チーム
- `Employee` - 従業員
- `Skill` - スキル

**依存関係：** 他の augur-* モジュールに依存せず、すべての他のモジュールの基礎となります。

### augur-persistence

**責任：** 統一された永続化レイヤー実装を提供し、複数のデータベースバックエンドをサポートします。

**主な機能：**
- 複数データベースのサポート（SQLite、PostgreSQL）
- 統一された Repository インターフェース設計
- データベースマイグレーション管理
- エンティティ型の永続化サポート

**サポートされるエンティティ型：**
- ユーザー
- 組織
- 部門
- ロール
- 対話
- メッセージ
- エージェント
- メモリ
- メモリタグ

**使用例：**
```rust
use augur_persistence::{AugurPersistence, PersistenceConfig, DatabaseType};

let config = PersistenceConfig::default();
let persistence = AugurPersistence::new(config).await?;

let user_repo = persistence.user_repository();
```

**依存関係：** `augur-types` に依存し、ビジネスロジックモジュールに依存されます。

### augur-file-system

**責任：** ローカルファイルシステムベースのファイルストレージサービスを提供します。

**主な機能：**
- ファイルのアップロードとダウンロード
- ファイルメタデータ管理
- ファイルアクセスレベル制御
- ファイル検索とフィルタリング
- ユーザーと組織のファイルリスト
- ファイルのコピーと移動操作
- 複数の MIME タイプ検出サポート

**使用例：**
```rust
use augur_file_system::{FsFileService, FsFileServiceConfig};

let config = FsFileServiceConfig::default();
let service = FsFileService::new(config).await?;
```

**依存関係：** `augur-types` に依存し、ビジネスロジックモジュールに依存されます。

### augur-memory

**責任：** メモリシステムを実装し、メモリの作成、保存、検索、管理をサポートします。

**主な機能：**
- メモリ CRUD 操作
- メモリタグ管理
- メモリ関係管理
- キーワード検索
- タグと時間範囲によるフィルタリング
- メモリのインポートとエクスポート
- 対話コンテキストの抽出
- 対話からのメモリ作成

**使用例：**
```rust
use augur_memory::AugurMemory;
use std::sync::Arc;

let memory_service = AugurMemory::new(
    Arc::new(memory_repository),
    Arc::new(memory_tag_repository),
);
```

**依存関係：** `augur-types`、`augur-persistence` に依存し、`augur-agent` などに依存されます。

### augur-agent

**責任：** エージェント（Agent）関連の型定義とインターフェースを提供し、エージェントのライフサイクルを管理します。

**主な機能：**
- エージェント型定義
- エージェント状態管理
- エージェント設定インターフェース
- エージェントライフサイクル管理

**依存関係：** `augur-types`、`augur-memory`、`augur-skill` に依存し、上位アプリケーションに依存されます。

### augur-orchestrator

**責任：** タスクオーケストレーションとワークフロー管理の型とインターフェースを提供します。

**主な機能：**
- タスクオーケストレーションインターフェース
- ワークフロー管理
- タスクスケジューリング
- 依存関係管理

**依存関係：** `augur-types` に依存し、上位アプリケーションに依存されます。

### augur-organization

**責任：** 組織、部門、ロール管理の型とインターフェースを提供します。

**主な機能：**
- 組織管理
- 部門構造
- ロール権限
- メンバー管理

**依存関係：** `augur-types`、`augur-persistence` に依存し、上位アプリケーションに依存されます。

### augur-skill

**責任：** スキルプラグインと能力拡張の型とインターフェースを提供します。

**主な機能：**
- スキルプラグインインターフェース
- スキル定義
- スキル実行
- プラグイン管理

**依存関係：** `augur-types` に依存し、`augur-agent` に依存されます。

## モジュール間連携例

### 例 1：エージェントによるタスク実行

1. 上位アプリケーションが `augur-orchestrator` を呼び出してタスクを開始
2. `augur-orchestrator` が利用可能な `augur-agent` エージェントを検索
3. `augur-agent` が `augur-skill` を使用して必要なスキルを読み込み
4. 実行中、`augur-agent` が `augur-memory` を使用してメモリを記録および検索
5. すべての状態変更が `augur-persistence` を通じて永続化

### 例 2：組織連携

1. 上位アプリケーションが `augur-organization` を通じて組織アーキテクチャを管理
2. `augur-organization` が `augur-persistence` を使用して組織データを保存
3. ユーザーがアップロードしたファイルが `augur-file-system` を通じて管理
4. 組織内のエージェントが `augur-agent` を通じて連携

## 設計原則

実装レイヤーは以下の設計原則に従います：

1. **単一責任原則** - 各モジュールは明確な機能領域のみを担当
2. **依存性逆転原則** - 上位モジュールは下位モジュールに依存せず、両方とも抽象に依存
3. **インターフェース分離原則** - 最小限のインターフェースを提供し、太ったインターフェースを回避
4. **モジュール化設計** - 明確な境界と依存関係を通じてモジュール間で連携
5. **テスト容易性** - 各モジュールは独立してテストしやすくする必要がある

## 拡張ガイド

新機能を追加する必要がある場合は、以下の手順に従ってください：

1. 機能が既存のどのモジュールに属するか、または新しいモジュールを作成する必要があるかを決定
2. `augur-types` で必要なデータ構造とエラー型を定義
3. 対応するビジネスモジュールでコアロジックを実装
4. 永続化が必要な場合は、`augur-persistence` に Repository を追加
5. ファイルストレージが必要な場合は、`augur-file-system` を使用
6. 本ドキュメントを更新し、新機能の説明を記録
