# セキュリティモデル

本ドキュメントでは、Skynet プロトコル上のサブネット実装としての AI Company が、アーキテクチャレベルでセキュリティメカニズムを補完する方法について説明します。

## 概要

### 階層的責任分担

| レイヤー | 担当内容 | 説明 |
|---------|---------|------|
| **Skynet プロトコルレイヤー** | ネットワーク通信、基礎暗号プリミティブ、サブネット抽象 | 軽量、柔軟、汎用 |
| **サブネット実装レイヤー（AI Company）** | 特定シナリオ向けセキュリティメカニズム、クライアント実装ガイド | サブネットタイプに応じて実装 |

Skynet プロトコルは**最小限必要**なセキュリティメカニズムのみを定義し、軽量性と柔軟性を維持します。特定のサブネット（AI Company など）は、自身のニーズに応じてアーキテクチャレイヤーで追加のセキュリティ対策を補完します。

---

## 一、メタデータ保護

### Skynet プロトコルレイヤーの位置付け
Skynet プロトコルは**メタデータ保護を提供しません**。プロトコルの軽量性を維持します。

### AI Company サブネットレイヤーでの実装

エンタープライズ向けアプリケーションの場合、メタデータ保護スキームは AI Company が設計・実装を担当します：

#### ベースライン対策（推奨）
| 対策 | 説明 |
|------|------|
| **ルーティングランダム化** | クライアントがサービスノードをランダムに選択 |
| **タイムスタンプ精度の低下** | ミリ秒単位ではなく秒単位の精度 |

#### 長期計画：ハイブリッドネットワーク
強力なメタデータ保護が必要な場合、AI Company は将来のバージョンでハイブリッドネットワーク（Loopix など）を導入できますが、以下が必要です：
- 大幅なアーキテクチャ変更
- より高い遅延と帯域幅オーバーヘッドの受け入れ
- プライバシー要件が非常に高いシナリオにのみ適用

## 二、耐量子暗号（PQC）移行

### Skynet プロトコルレイヤーの位置付け
Skynet プロトコルは**拡張ポイントを確保**し、PQC アルゴリズムの移行をサポートしますが、強制はしません。

### AI Company サブネットレイヤーでの実装

#### 2.1 ハイブリッド証明書モード
AI Company は、古典暗号とポスト量子暗号の両方を同時にサポートする実装を担当します：
- **デュアルキーペア**：各アイデンティティは Ed25519 と CRYSTALS-Dilithium のキーペアを同時に保持
- **デュアル署名**：重要な操作は両方のアルゴリズムで同時に署名
- **段階的移行**：まず検証をサポートし、次第に PQC 主体に切り替え

#### 2.2 PQC 暗号スイート
| コンポーネント | 古典アルゴリズム | PQC アルゴリズム | ハイブリッドモード |
|---------------|-----------------|-----------------|------------------|
| **署名** | Ed25519 | CRYSTALS-Dilithium | Ed25519 + Dilithium |
| **鍵カプセル化** | X25519 | CRYSTALS-Kyber | X25519 + Kyber |
| **ハッシュ** | Blake3 | Blake3 | Blake3 |

#### 2.3 鍵ローテーション戦略
- **緊急ローテーション**：量子の脅威が発見された場合、即座にネットワーク全体の鍵ローテーションをトリガー可能
- **定期ローテーション**：デフォルトで 90 日ごとに長期鍵をローテーション
- **前方秘匿性**：セッション鍵は PQC KEM を使用して前方秘匿性を確保

### 移行ロードマップ
```
フェーズ 1（現在）：古典暗号主体
    ↓
フェーズ 2：ハイブリッドモード（古典と PQC を同時にサポート）
    ↓
フェーズ 3：PQC 主体、古典は代替として
    ↓
フェーズ 4：完全 PQC（古典アルゴリズムサポートの削除）
```

## 三、クライアントセキュリティ実装ガイド（AI Company サブネットレイヤー）

### Skynet プロトコルレイヤーの位置付け
Skynet プロトコルは**インターフェースを定義**しますが、具体的な実装はクライアントとサブネットレイヤーに委ねます。

### AI Company サブネットレイヤーの仕様

#### 3.1 鍵管理仕様

##### 鍵ストレージ階層
| 鍵タイプ | 保存場所 | 暗号化保護 |
|---------|---------|----------|
| **アイデンティティ秘密鍵** | システムキーチェーン / HSM / TEE | ハードウェアレベルの保護 |
| **デバイス秘密鍵** | 暗号化されたローカルストレージ | ユーザーパスワード派生鍵 |
| **セッション鍵** | メモリ（プロセス分離） | 自動破棄 |

##### 鍵派生要件
- **アルゴリズム**：Argon2id の使用を強制
- **パラメータ**：
  - メモリ：最低 64MB
  - 反復回数：最低 3 回
  - 並列度：4
  - ソルト：16 バイト CSPRNG で生成

##### 鍵バックアップと回復
- **Shamir 秘密分散**：回復鍵を 5 つに分割し、3 つで回復可能
- **オフラインストレージ**：ユーザーに回復鍵の印刷またはオフラインデバイスへの保存を推奨
- **ソーシャルリカバリー**：信頼できる連絡先による回復支援をオプションでサポート

#### 3.2 API Key 管理仕様（AI Company 固有）

##### API Key セキュリティ原則
| 原則 | 説明 |
|------|------|
| **最小権限** | 各 API Key はタスク完了に必要な最小限の権限のみを付与 |
| **短期有効** | 恒久的な API Key よりも短期 Token を優先 |
| **分離使用** | 異なる Agent/サービスでは異なる API Key を使用 |
| **取り消し可能** | 漏洩または不要になった API Key はいつでも取り消し可能 |

##### API Key ストレージ
- **保存場所**：システムキーチェーン / セキュリティキー管理サービス（KMS）
- **暗号化保護**：マスターキーで API Key を暗号化して静的暗号化
- **メモリ保護**：使用後は即座にメモリから消去し、ディスクへのスワップを回避

##### API Key ライフサイクル管理
```
作成 → 配布 → 使用 → ローテーション → 取り消し → 破棄
```

**作成**：
- CSPRNG を使用して十分な強度の API Key を生成（少なくとも 256 ビットエントロピー）
- 作成日時、作成者、用途、権限範囲を記録

**配布**：
- 安全なチャネルで転送（エンドツーエンド暗号化）
- ログやエラーメッセージで完全な API Key を公開しない
- 識別用に Key の前後数桁のみを表示

**使用**：
- ハードコーディングするのではなく、環境変数または安全な設定ファイルで注入
- リクエストヘッダーまたは認証フィールドで渡す（`Authorization: Bearer <key>` など）
- URL クエリパラメータで渡さない

**ローテーション**：
- 定期的にローテーション（デフォルト 90 日）
- 新旧 Key の共存移行期間をサポート（少なくとも 7 日）
- セキュリティイベント発生時は即座にローテーション

**取り消し**：
- セルフサービスの取り消しインターフェースを提供
- 取り消し後は即座に無効化
- 取り消し理由と日時を記録

**破棄**：
- すべてのストレージ場所から削除
- メモリとディスクの残留を上書き
- 破棄完了を確認

##### API Key 漏洩緊急対応
1. **即座に取り消し**：漏洩発見後、最初に取り消し
2. **監査ログ**：当該 Key のすべての使用記録を確認
3. **影響評価**：漏洩による損失の可能性を評価
4. **ユーザー通知**：影響を受けるユーザー/チームに通知
5. **根本原因分析**：漏洩原因を特定し、再発防止
6. **セキュリティ強化**：ストレージと使用方法を改善

##### 一時 Token 優先
Agent シナリオでは、恒久的な API Key よりも短期 Token を優先します：
- **OAuth 2.0**：Client Credentials または Authorization Code Flow を使用
- **JWT**：短期 JWT Token（有効期間 < 1 時間）
- **動的リフレッシュ**：Refresh Token を使用して新しい Access Token を取得

#### 3.3 乱数生成仕様

##### エントロピーソース要件
- **主要エントロピーソース**：OS の CSPRNG（Windows: `CryptGenRandom`, Linux: `/dev/urandom`）
- **補完エントロピーソース**：
  - デバイスセンサーデータ（加速度計、ジャイロスコープ）
  - ユーザーインタラクションタイムスタンプ
  - ネットワーク遅延測定
- **エントロピー混合**：Fortuna または Yarrow アルゴリズムを使用して複数ソースのエントロピーを混合

##### CSPRNG 検証
- NIST SP 800-90A 標準を実装
- 定期的にランダム性テストを実施（Dieharder、TestU01）
- 暗号学的に安全でない乱数生成器の使用を禁止

#### 3.4 リファレンス実装（AI Company サブネット SDK）
公式 SDK を提供し、以下を含みます：
- **暗号ライブラリラッパー**：統一された暗号プリミティブインターフェース
- **鍵管理モジュール**：そのまま使用できる安全な鍵ストレージ
- **API Key 管理モジュール**：安全な API Key ライフサイクル管理

## 四、セキュリティ監査とログ（AI Company 担当）

### Skynet プロトコルレイヤーの位置付け
監査ログは**Skynet プロトコルに含まれません**。完全にサブネット作成者がニーズに応じて自主的に実装します。

### 理由
サブネットタイプによって監査ニーズは大きく異なります：

| サブネットタイプ | 監査ニーズ | 例 |
|-----------------|----------|-----|
| **組織サブネット（AI Company）** | 高要求 | 完全な監査ログ、改ざん不可、長年保存、コンプライアンス認証 |
| **コミュニティサブネット** | 中要求 | 基本操作ログ、オプションで保存 |
| **プライベートサブネット** | 低要求 | 監査ログが不要な場合もある |

### AI Company サブネットでの実装

AI Company はエンタープライズ向けサブネットとして、完全な監査ログ機能の実装を担当します：

#### 4.1 監査イベントタイプ
- アイデンティティ認証イベント
- 鍵/API Key 操作
- 権限変更
- 機密リソースアクセス

#### 4.2 ログセキュリティ要件
- **クライアントローカルストレージ**：監査ログはクライアントが収集・保存
- **暗号化保護**：機密監査ログは暗号化して保存
- **完全性保護**：デジタル署名を使用して改ざんを防止
- **サブネットレベル設定**：サブネット作成者は監査ポリシーを定義可能

## 五、シビルアタック防御（AI Company 担当）

### Skynet プロトコルレイヤーの位置付け
Skynet プロトコルは**シビルアタック防御を強制しません**。プロトコルの柔軟性を維持します。

### AI Company サブネットレイヤーでの実装

#### 5.1 多層防御システム

| 防御レイヤー | メカニズム | 説明 |
|------------|----------|------|
| **第一層** | アイデンティティ認証 | メール、電話番号、WebAuthn など |
| **第二層** | プルーフ・オブ・ワーク | Hashcash または同様のメカニズム |
| **第三層** | ソーシャルグラフ検証 | 信頼できる連絡先による裏付け |
| **第四層** | 経済的担保 | 保証金として Token をロック |

#### 5.2 アイデンティティ認証オプション
- **WebAuthn/FIDO2**：推奨の強力な認証方式
- **メール認証**：確認リンクを送信
- **電話番号認証**：SMS 確認コード
- **OAuth**：サードパーティアイデンティティプロバイダーをサポート（Google、GitHub など）

#### 5.3 レピュテーションシステム
- **初期レピュテーション**：新規ユーザーは低レピュテーションで操作頻度を制限
- **レピュテーション蓄積**：通常使用で徐々にレピュテーションが向上
- **レピュテーションペナルティ**：悪意のある行動でレピュテーションが低下
- **クロスサブネットレピュテーション**：レピュテーションは異なるサブネット間で共有可能

## 六、前方秘匿性強化（サブネットレイヤー実装ガイド）

### Skynet プロトコルレイヤーの位置付け
Skynet プロトコルは**Double Ratchet と MLS を使用**して前方秘匿性を提供しますが、具体的な実装詳細はクライアントが担当します。

### AI Company サブネットレイヤーの仕様

#### 6.1 鍵破棄仕様

##### メモリ鍵破棄
- **ゼロ上書き**：memset_s または同等の関数を使用して鍵メモリを上書き
- **複数回上書き**：少なくとも 3 回の異なるパターンで上書き
- **メモリロック**：mlock/VirtualLock を使用して鍵のディスクへのスワップを防止

##### 永続化鍵破棄
- **安全な削除**：shred または同等のツールを使用
- **SSD 処理**：SSD に対する特別な処理（TRIM、安全消去）
- **破棄の確認**：鍵マテリアルが復元不能であることを確認

#### 6.2 前方秘匿性保証
- **セッション鍵の短命化**：メッセージごとに鍵をローテーション（Double Ratchet）
- **鍵キャッシュなし**：古いメッセージの復号に使用できる鍵をキャッシュしない
- **完全前方秘匿性（PFS）**：PFS プロパティを明示的に保証

## 七、セキュリティ境界と深層防御（AI Company サブネットレイヤー）

### 7.1 セキュリティ境界の定義

| 境界 | 保護対策 |
|------|---------|
| **クライアント境界** | サンドボックス分離、プロセス分離、メモリ保護 |
| **ネットワーク境界** | TLS 1.3、証明書ピンニング、証明書透過性 |
| **サービスノード境界** | 最小権限、ネットワーク分離、侵入検知 |
| **データ境界** | エンドツーエンド暗号化、静的暗号化、アクセス制御 |

### 7.2 深層防御戦略

```
第一層：クライアントセキュリティ
    ↓
第二層：伝送セキュリティ（TLS 1.3 + Noise）
    ↓
第三層：エンドツーエンド暗号化（X3DH + Double Ratchet / MLS）
    ↓
第四層：マルチノード検証
    ↓
第五層：監査ログと異常検知（オプション）
```

## 八、セキュリティコンプライアンスと認証（AI Company サブネットレイヤー）

### 8.1 コンプライアンス基準（必要に応じて満足）
- **GDPR**：データ保護、ユーザー制御、ポータビリティ
- **HIPAA**（該当する場合）：医療データ保護
- **SOC 2**：セキュリティ、可用性、機密性
- **ISO 27001**：情報セキュリティマネジメントシステム

### 8.2 セキュリティ認証（オプション）
- **第三者監査**：定期的に独立したセキュリティ監査を実施
- **バグバウンティ**：脆弱性報奨金プログラムを確立
- **公開透明性**：セキュリティ監査レポートを公開

## まとめ

### 階層的責任のレビュー

| レイヤー | 責任 |
|---------|------|
| **Skynet プロトコルレイヤー** | 軽量で柔軟な基盤の提供：暗号プリミティブ、ネットワーク通信、サブネット抽象 |
| **AI Company サブネットレイヤー** | エンタープライズ向けセキュリティ実装：API Key 管理、監査ログ、コンプライアンス認証など |

### 明確な責任分担

| セキュリティ領域 | Skynet プロトコル | AI Company |
|-----------------|-----------------|------------|
| **メタデータ保護** | 提供しない | 実装担当 |
| **耐量子破解** | 拡張ポイントを確保 | 実装担当 |
| **API Key 管理** | 関与しない | 担当 |
| **監査ログ** | 含まれない | 担当 |
| **シビル防御** | 強制しない | 担当 |

### AI Company セキュリティモデルの補完

Skynet 上のエンタープライズ向けサブネット実装として、AI Company セキュリティモデルは以下の方法でプロトコルレイヤーを補完します：

1. **メタデータ保護**：AI Company が実装担当、ベースライン対策と長期計画を提供
2. **耐量子移行**：AI Company が実装担当、ハイブリッド証明書モード、段階的移行ロードマップ
3. **クライアントセキュリティ**：鍵管理仕様、API Key 管理仕様、乱数生成仕様、公式 SDK
4. **監査ログ**：AI Company が実装担当、完全な監査ログ機能
5. **シビル防御**：AI Company が実装担当、多層防御、アイデンティティ認証、レピュテーションシステム
6. **前方秘匿性**：鍵破棄仕様、PFS 保証
7. **コンプライアンス認証**：GDPR、SOC 2、ISO 27001

両者が組み合わさることで、Skynet プロトコル自体の軽量性と柔軟性を維持しながら、完全なエンタープライズ向けセキュリティシステムを構成します。
