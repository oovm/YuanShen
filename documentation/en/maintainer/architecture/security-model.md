# Security Model

This document describes how AI Company, as a subnet implementation on the Skynet Protocol, supplements security mechanisms at the architectural level.

## Overview

### Layered Responsibility Division

| Layer | Responsibilities | Description |
|-------|-------------------|-------------|
| **Skynet Protocol Layer** | Network communication, basic cryptographic primitives, subnet abstraction | Lightweight, flexible, universal |
| **Subnet Implementation Layer (AI Company)** | Scenario-specific security mechanisms, client implementation guidelines | Implemented as needed based on subnet type |

The Skynet Protocol defines only the **minimally necessary** security mechanisms, maintaining lightweight and flexible design. Specific subnets (like AI Company) supplement additional security measures at the architectural layer according to their own requirements.

---

## 1. Metadata Protection

### Skynet Protocol Layer Positioning
The Skynet Protocol **does not provide** metadata protection, maintaining protocol lightweightness.

### AI Company Subnet Layer Responsibility

For enterprise-level applications, metadata protection solutions are designed and implemented by AI Company:

#### Baseline Measures (Recommended)
| Measure | Description |
|---------|-------------|
| **Route Randomization** | Clients randomly select service nodes |
| **Timestamp Precision Reduction** | Second-level precision (rather than milliseconds) |

#### Long-term Plan: Mix Network
If strong metadata protection is required, AI Company may introduce mix networks (such as Loopix) in future versions, but this requires:
- Significant architectural changes
- Acceptance of higher latency and bandwidth overhead
- Only suitable for scenarios with extremely high privacy requirements

## 2. Post-Quantum Cryptography (PQC) Migration

### Skynet Protocol Layer Positioning
The Skynet Protocol **reserves extension points** to support PQC algorithm migration, but does not mandate it.

### AI Company Subnet Layer Responsibility

#### 2.1 Hybrid Certificate Mode
AI Company is responsible for implementing simultaneous support for both classical and post-quantum cryptography:
- **Dual Key Pairs**: Each identity holds both Ed25519 and CRYSTALS-Dilithium key pairs
- **Dual Signatures**: Important operations are signed using both algorithms simultaneously
- **Gradual Migration**: First support verification, then gradually switch to PQC as primary

#### 2.2 PQC Cipher Suites
| Component | Classical Algorithm | PQC Algorithm | Hybrid Mode |
|-----------|---------------------|---------------|-------------|
| **Signatures** | Ed25519 | CRYSTALS-Dilithium | Ed25519 + Dilithium |
| **Key Encapsulation** | X25519 | CRYSTALS-Kyber | X25519 + Kyber |
| **Hashing** | Blake3 | Blake3 | Blake3 |

#### 2.3 Key Rotation Strategy
- **Emergency Rotation**: Full network key rotation can be triggered immediately when quantum threats are detected
- **Regular Rotation**: Default rotation every 90 days for long-term keys
- **Forward Security**: Session keys use PQC KEM to ensure forward security

### Migration Roadmap
```
Phase 1 (Current): Classical cryptography primary
    ↓
Phase 2: Hybrid mode (supports both classical and PQC)
    ↓
Phase 3: PQC primary, classical as backup
    ↓
Phase 4: Full PQC (remove classical algorithm support)
```

## 3. Client Security Implementation Guidelines (AI Company Subnet Layer)

### Skynet Protocol Layer Positioning
The Skynet Protocol **defines interfaces** but leaves specific implementation to clients and the subnet layer.

### AI Company Subnet Layer Specifications

#### 3.1 Key Management Specifications

##### Key Storage Hierarchy
| Key Type | Storage Location | Encryption Protection |
|----------|------------------|----------------------|
| **Identity Private Key** | System keychain / HSM / TEE | Hardware-level protection |
| **Device Private Key** | Encrypted local storage | User password-derived key |
| **Session Key** | Memory (process isolation) | Automatic destruction |

##### Key Derivation Requirements
- **Algorithm**: Mandatory use of Argon2id
- **Parameters**:
  - Memory: At least 64MB
  - Iterations: At least 3 times
  - Parallelism: 4
  - Salt: 16 bytes generated by CSPRNG

##### Key Backup and Recovery
- **Shamir Secret Sharing**: Split recovery key into 5 shares, 3 shares can recover
- **Offline Storage**: Encourage users to print or store recovery keys on offline devices
- **Social Recovery**: Optional support for trusted contacts to assist recovery

#### 3.2 API Key Management Specifications (AI Company Specific)

##### API Key Security Principles
| Principle | Description |
|-----------|-------------|
| **Least Privilege** | Each API Key is granted only the minimum permissions required to complete tasks |
| **Short-lived Validity** | Prioritize using short-term tokens rather than permanent API Keys |
| **Isolated Usage** | Different Agents/services use different API Keys |
| **Revocable** | API Keys can be revoked at any time if leaked or no longer needed |

##### API Key Storage
- **Storage Location**: System keychain / Security Key Management Service (KMS)
- **Encryption Protection**: At-rest encryption, encrypt API Keys using master keys
- **Memory Protection**: Immediately clear from memory after use, avoid swapping to disk

##### API Key Lifecycle Management
```
Create → Distribute → Use → Rotate → Revoke → Destroy
```

**Create**:
- Use CSPRNG to generate sufficiently strong API Keys (at least 256 bits of entropy)
- Record creation time, creator, purpose, permission scope

**Distribute**:
- Transmit via secure channel (end-to-end encryption)
- Avoid exposing full API Key in logs, error messages
- Only display first/last few characters of Key for identification

**Use**:
- Inject via environment variables or secure configuration files, rather than hardcoding
- Pass using request headers or authorization fields (such as `Authorization: Bearer <key>`)
- Avoid passing in URL query parameters

**Rotate**:
- Regular rotation (default 90 days)
- Support transition period with both old and new Keys coexisting (at least 7 days)
- Immediately rotate when security events are triggered

**Revoke**:
- Provide self-service revocation interface
- Immediately invalidate after revocation
- Record revocation reason and time

**Destroy**:
- Delete from all storage locations
- Overwrite residues in memory and disk
- Verify destruction is complete

##### API Key Leak Incident Response
1. **Immediate Revocation**: Revoke at the first moment leak is discovered
2. **Audit Logs**: Check all usage records of the Key
3. **Impact Assessment**: Assess potential damage from the leak
4. **Notify Users**: Notify affected users/teams
5. **Root Cause Analysis**: Identify leak cause to prevent recurrence
6. **Security Hardening**: Improve storage and usage methods

##### Temporary Token Priority
For Agent scenarios, prioritize short-term tokens rather than permanent API Keys:
- **OAuth 2.0**: Use Client Credentials or Authorization Code Flow
- **JWT**: Short-term JWT Tokens (validity < 1 hour)
- **Dynamic Refresh**: Use Refresh Token to obtain new Access Token

#### 3.3 Random Number Generation Specifications

##### Entropy Source Requirements
- **Primary Entropy Source**: Operating system CSPRNG (Windows: `CryptGenRandom`, Linux: `/dev/urandom`)
- **Supplementary Entropy Sources**:
  - Device sensor data (accelerometer, gyroscope)
  - User interaction timestamps
  - Network latency measurements
- **Entropy Mixing**: Use Fortuna or Yarrow algorithms to mix multi-source entropy

##### CSPRNG Validation
- Implement NIST SP 800-90A standard
- Regularly perform randomness tests (Dieharder, TestU01)
- Prohibit use of any non-cryptographically secure random number generators

#### 3.4 Reference Implementation (AI Company Subnet SDK)
Provide official SDK, including:
- **Cryptography Library Wrapper**: Unified cryptographic primitive interfaces
- **Key Management Module**: Out-of-the-box secure key storage
- **API Key Management Module**: Secure API Key lifecycle management

## 4. Security Auditing and Logging (AI Company Responsibility)

### Skynet Protocol Layer Positioning
Audit logs **are not included in the Skynet Protocol**, completely implemented by subnet creators according to their own requirements.

### Reason
Audit requirements vary greatly among different subnet types:

| Subnet Type | Audit Requirements | Example |
|-------------|-------------------|---------|
| **Organization Subnet (AI Company)** | High requirements | Complete audit logs, tamper-proof, multi-year retention, compliance certification |
| **Community Subnet** | Medium requirements | Basic operation logs, optional retention |
| **Private Subnet** | Low requirements | May not require any audit logs |

### AI Company Subnet Responsibility

AI Company, as an enterprise-level subnet, is responsible for implementing complete audit logging functionality:

#### 4.1 Audit Event Types
- Identity authentication events
- Key/API Key operations
- Permission changes
- Sensitive resource access

#### 4.2 Log Security Requirements
- **Client Local Storage**: Audit logs are collected and stored by clients
- **Encryption Protection**: Sensitive audit logs are stored encrypted
- **Integrity Protection**: Use digital signatures to prevent tampering
- **Subnet-level Configuration**: Subnet creators can define audit policies

## 5. Sybil Attack Protection (AI Company Responsibility)

### Skynet Protocol Layer Positioning
The Skynet Protocol **does not mandate** Sybil attack protection, maintaining protocol flexibility.

### AI Company Subnet Layer Responsibility

#### 5.1 Multi-layer Protection System

| Protection Layer | Mechanism | Description |
|------------------|-----------|-------------|
| **First Layer** | Identity Verification | Email, phone number, WebAuthn, etc. |
| **Second Layer** | Proof of Work | Hashcash or similar mechanisms |
| **Third Layer** | Social Graph Verification | Trusted contact endorsements |
| **Fourth Layer** | Economic Staking | Lock tokens as security deposit |

#### 5.2 Identity Verification Options
- **WebAuthn/FIDO2**: Recommended strong authentication method
- **Email Verification**: Send verification link
- **Phone Number Verification**: SMS verification code
- **OAuth**: Support third-party identity providers (Google, GitHub, etc.)

#### 5.3 Reputation System
- **Initial Reputation**: New users have low reputation, operation frequency limited
- **Reputation Accumulation**: Normal usage gradually increases reputation
- **Reputation Penalty**: Malicious behavior reduces reputation
- **Cross-subnet Reputation**: Reputation can be shared between different subnets

## 6. Forward Secrecy Enhancement (Subnet Layer Implementation Guidelines)

### Skynet Protocol Layer Positioning
The Skynet Protocol **uses** Double Ratchet and MLS to provide forward secrecy, but specific implementation details are the responsibility of clients.

### AI Company Subnet Layer Specifications

#### 6.1 Key Destruction Specifications

##### In-memory Key Destruction
- **Zero Overwrite**: Use memset_s or equivalent functions to overwrite key memory
- **Multiple Overwrites**: At least 3 overwrites with different patterns
- **Memory Locking**: Use mlock/VirtualLock to prevent keys from swapping to disk

##### Persistent Key Destruction
- **Secure Deletion**: Use shred or equivalent tools
- **SSD Handling**: Special treatment for SSDs (TRIM, secure erase)
- **Verify Destruction**: Confirm key material cannot be recovered

#### 6.2 Forward Secrecy Guarantees
- **Short-lived Session Keys**: Rotate keys per message (Double Ratchet)
- **No Key Caching**: Do not cache any keys that could be used to decrypt old messages
- **Perfect Forward Secrecy (PFS)**: Explicitly guarantee PFS properties

## 7. Security Boundaries and Defense-in-Depth (AI Company Subnet Layer)

### 7.1 Security Boundary Definition

| Boundary | Protection Measures |
|----------|---------------------|
| **Client Boundary** | Sandbox isolation, process isolation, memory protection |
| **Network Boundary** | TLS 1.3, certificate pinning, certificate transparency |
| **Service Node Boundary** | Least privilege, network isolation, intrusion detection |
| **Data Boundary** | End-to-end encryption, at-rest encryption, access control |

### 7.2 Defense-in-Depth Strategy

```
Layer 1: Client Security
    ↓
Layer 2: Transport Security (TLS 1.3 + Noise)
    ↓
Layer 3: End-to-end Encryption (X3DH + Double Ratchet / MLS)
    ↓
Layer 4: Multi-node Verification
    ↓
Layer 5: Audit Logs and Anomaly Detection (Optional)
```

## Summary

### Layered Responsibility Review

| Layer | Responsibility |
|-------|----------------|
| **Skynet Protocol Layer** | Provide lightweight, flexible foundation: cryptographic primitives, network communication, subnet abstraction |
| **AI Company Subnet Layer** | Enterprise-level security implementation: API Key management, audit logs, compliance certification, etc. |

### Clear Responsibility Division

| Security Domain | Skynet Protocol | AI Company |
|-----------------|-----------------|------------|
| **Metadata Protection** | Not provided | Responsible for implementation |
| **Post-Quantum Resistance** | Reserve extension points | Responsible for implementation |
| **API Key Management** | Not involved | Responsible |
| **Audit Logs** | Not included | Responsible |
| **Sybil Protection** | Not mandated | Responsible |

### AI Company Security Model Supplement

As an enterprise-level subnet implementation on Skynet, the AI Company Security Model supplements the protocol layer in the following ways:

1. **Metadata Protection**: AI Company is responsible for implementation, providing baseline measures and long-term plans
2. **Post-Quantum Migration**: AI Company is responsible for implementation, hybrid certificate mode, gradual migration roadmap
3. **Client Security**: Key management specifications, API Key management specifications, random number generation specifications, official SDK
4. **Audit Logs**: AI Company is responsible for implementation, complete audit log functionality
5. **Sybil Protection**: AI Company is responsible for implementation, multi-layer protection, identity verification, reputation system
6. **Forward Secrecy**: Key destruction specifications, PFS guarantees
7. **Compliance Certification**: GDPR, SOC 2, ISO 27001

The combination of the two constitutes a complete enterprise-level security system, while maintaining the lightweightness and flexibility of the Skynet Protocol itself.
