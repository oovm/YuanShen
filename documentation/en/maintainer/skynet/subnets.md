# Subnet Model

## Subnet Identifier

Each subnet has a unique ID `subnet_id = blake3(arbitrary bytes)`, which can be generated by the creator. The mainnet is a predefined subnet with a fixed ID of all zeros (`0x00...`).

## Subnet Type

The subnet type is an open string identifier used to distinguish the function and purpose of subnets. Clients can decide whether to load and how to handle a subnet based on its type.

**Common Subnet Type Examples**:

| Subnet Type | Description | Usage Example |
|-------------|-------------|---------------|
| **organization** | Organization subnet | For organization and company communication and collaboration |
| **community** | Community subnet | For general community and interest group communication |
| **private** | Private subnet | For small private group communication |

**Purpose of Subnet Type**:
- Clients can decide whether to load and how to handle a subnet based on its type
- Different types of subnets can have different functional features and permission policies
- Clients can selectively load and display subnets based on type
- The subnet type is open, and applications can define their own types

## Subnet Metadata

Each subnet contains metadata describing its basic attributes and functionality:

| Attribute | Description | Type |
|-----------|-------------|------|
| **subnet_type** | Subnet type | String (open type, e.g., organization/community/private) |
| **subnet_version** | Subnet type version | String (e.g., "1.0.0") |
| **name** | Subnet name | String |
| **description** | Subnet description | String (optional) |
| **icon** | Subnet icon | URL or hash (optional) |
| **created_at** | Creation time | Timestamp |
| **created_by** | Creator | user_id |
| **features** | Feature list | String array (optional) |
| **metadata** | Custom metadata | JSON object (optional) |

**Purpose of Subnet Metadata**:
- Clients use `subnet_type` to determine if they support the subnet
- `subnet_type_version` is used for version compatibility checks
- The `features` list declares the functional features supported by the subnet
- `metadata` can be used to store type-specific extension information

## Subnet Model Concepts

Skynet adopts a subnet model where each independent communication system or community is a subnet:
- Each subnet has its own users, contacts, and groups
- Users can join multiple subnets simultaneously using the same `auth_id`
- Each subnet has independent contacts and groups (contacts are an internal subnet concept)

## Core Subnet Identifiers

As a decentralized communication protocol, Skynet has three core identifiers for subnets:

| Identifier | Description | Purpose |
|------------|-------------|---------|
| **auth_id** | User global identity ID | Uniquely identifies a user across subnets, similar to a real name. **The highest secret of the Skynet protocol, used only for identity authentication, and should never be leaked or stored in subnet-internal data.** |
| **user_id** | User's local ID within the subnet | Local identifier within the subnet, similar to a nickname/screen name, used for privacy protection. **All data within the subnet only uses user_id.** |
| **channel_id** | Channel/group ID | Identifies a chat group or channel within the subnet |

## Subnet Data

Each subnet maintains the following data and uses **multi-node replication** for storage:

### 1. Subnet Metadata

- **subnet_type**: Subnet type (open string, e.g., organization/community/private)
- **subnet_type_version**: Subnet type version
- **name**: Subnet name
- **description**: Subnet description (optional)
- **icon**: Subnet icon (optional)
- **created_at**: Creation time
- **created_by**: Creator's user_id
- **features**: Feature list (optional)
- **metadata**: Custom metadata (optional)

### 2. Member List
- **user_id**: User's local ID within the subnet (unique within the subnet, optional)
- **Identity Public Key**: User's Ed25519 public key (for signature verification)
- **Role**: Admin / Regular member
- **Join Time**: When the user joined the subnet
- **Device Public Key List**: User's device public keys used within this subnet (for end-to-end encryption)
- **Contact List**: This user's contacts within the subnet (an internal subnet concept, only uses user_id)
- **User Metadata (Profile)**:
  - **avatar**: Avatar (resource reference or URL, optional)
  - **nickname**: Nickname (display name within the subnet, optional)
  - **bio**: Personal bio (optional)
  - **status_text**: Custom status text (e.g., "In a meeting", "Eating out", optional)
  - **presence_status**: Online status (online/busy/away/offline, optional)
  - **last_active_at**: Last active time (timestamp, optional)
  - **updated_at**: Metadata update time (timestamp, optional)
  - **device_info**: Device information (JSON object, optional, e.g., device type, operating system, etc.)

**Note**: `auth_id` is only used for initial identity authentication and should never be stored in the subnet member list or any subnet-internal data.

### 2.1 Subnet Mode: Open vs Closed
Subnets support two operating modes:
| Mode | Description | Use Case |
|------|-------------|----------|
| **Closed Subnet** | Joining requires admin approval, preventing Sybil attacks | Enterprises, organizations, private communities |
| **Open Subnet** | Anyone can join freely without approval | Public communities, interest groups |

The mode is specified when creating the subnet and can later be modified by admins.

### 3. Channel List
- **channel_id**: Unique ID of the channel/group
- **Channel Name**: Group name
- **Creator**: Creator's user_id
- **Creation Time**: Creation time
- **Member List**: List of channel member user_ids
- **Channel Type**: Private chat / Group chat / Announcement channel

### 4. Permission Policy
- Who can add/remove members
- Who can create/delete channels
- Who can modify channel information

### 5. Resources

Resources are accessible entities within the subnet, stored and managed by subnet maintenance nodes. See [Resource Model](./resources.md) for details.

### 6. Messages

Messages are the content units transmitted within the subnet for user-to-user communication. See [Message Model](./messages.md) for details.

## Subnet Maintenance Nodes

Each subnet is maintained by a set of service nodes called **maintenance nodes** responsible for storing and synchronizing data. When creating a subnet, the creator can specify initial maintenance nodes (usually nodes they trust), and later add/remove maintenance nodes through subnet voting or admin assignment.

Maintenance nodes maintain data consistency through **Byzantine fault-tolerant replication**.
