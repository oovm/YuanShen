# Skynet 協定設計草案

## 1. 概述
Skynet 是一個去中心化通訊協定，旨在建構安全、隱私保護的即時通訊網路。其核心架構由**服務節點**組成一個對等網路，維護**主網**與**子網**兩級結構。客戶端可連接任意服務節點，並透過端到端加密實現裝置間安全通訊。協定設計遵循**零信任**原則：服務節點之間、服務節點與客戶端之間均假設對方可能惡意，所有關鍵資料必須經密碼學驗證。

### 2. 節點身分與網路發現
- **節點標識**：每個服務節點擁有一個長期 Ed25519 金鑰對，節點 ID 為公鑰的雜湊值（`NodeID = blake3(public_key)`）。節點間通訊使用 Noise 協定（XX 模式）建立加密通道，並相互驗證 NodeID。
- **網路發現**：
  - 初始節點透過預設定的種子節點清單加入網路。
  - 節點維護一個 Kademlia 風格的分散式雜湊表（DHT），用於儲存其他節點的位址資訊（IPv4/IPv6 + port）和活性探測。
  - 節點定期向 DHT 發布自己的位址，並刷新鄰居清單。
  - 每個節點需支援 STUN 協定輔助 NAT 穿透；無法穿透時，可透過其他節點中繼（TURN-like 功能，但中繼節點僅轉發加密資料）。

### 4. 使用者身分與認證
- **全域身分**：每個使用者擁有一個全域 UUID `auth_id`，以及一個長期 Ed25519 金鑰對（用於身分簽章）。使用者首次使用時生成該身分，公鑰由使用者自己簽章發布。**auth_id 是 Skynet 協定的最高機密，絕不應在子網內部資料中洩露或儲存。**
- **子網模型**：
  - 每個獨立的通訊系統或社群都是一個獨立的子網
  - 使用者在不同子網中有不同的聯絡人清單
  - `auth_id` 類似真名，跨子網唯一標識使用者，**僅用於使用者身分認證，不在子網內部資料中使用**
  - `user_id` 類似暱稱/網名，子網內本地標識，用於隱私保護，**子網內部所有資料只使用 user_id**
  - 使用者在子網內只使用 `user_id` 作為標識
  - 使用者在子網內的公鑰（可使用全域身分公鑰，也可單獨生成子網專用金鑰）需經自己簽章後提交給子網維護節點
  - 使用者可同時加入多個子網，使用同一個 `auth_id` 進行認證
  - **子網類型**：每個子網有類型標識（如 `organization`、`community`、`private`、`custom`），客戶端根據類型決定是否載入和如何處理
  - **子網元資訊**：每個子網包含元資訊（類型、版本、名稱、描述、功能特性等），用於客戶端識別和配接
- **客戶端認證**：
  - 客戶端連接服務節點時，需提供 `auth_id` 並完成挑戰-回應：服務節點發送隨機數，客戶端用身分私鑰簽章後回傳，服務節點驗證簽章。
  - 認證通過後，服務節點為該客戶端生成一個臨時會話金鑰（用於後續請求加密），並在會話有效期內維護客戶端的線上狀態。

### 5. 端到端加密
所有使用者間通訊內容（私聊、群聊訊息、檔案傳輸）均採用端到端加密，服務節點無法解密。加密方案借鑑 Signal 協定和 MLS 協定：
- **裝置金鑰**：每個客戶端裝置生成一個 X25519 金鑰對作為裝置標識，並用使用者身分私鑰簽章後發布到其所加入的子網中（作為成員清單的一部分）。使用者可擁有多個裝置。
- **私聊**：
  - 雙方透過 X3DH 金鑰交換協定建立共用金鑰，並使用雙棘輪演算法（Double Ratchet）生成會話金鑰，實現前向安全與後向安全。
  - 初始金鑰交換訊息可透過服務節點轉發（加密），服務節點僅傳遞密文。
- **群聊**：
  - 採用 MLS（Messaging Layer Security）協定，提供前向保密、後向保密和成員變化時的高效金鑰輪替。
  - MLS 協定自動處理成員加入/離開時的金鑰更新，無需管理員手動介入。
- **元資料保護**：
  - 服務節點只能看到訊息的接收者（目標子網和使用者/群組），但無法看到訊息內容。為隱藏接收者，可考慮使用混合網路（如 Loopix）技術，但初始版本暫不實作，留給後續擴充。

### 5.1 安全參數（效率優先）
Skynet 協定採用以下安全參數，在保證企業級安全性的前提下優先考慮效能和使用者體驗：
| 參數 | 取值 | 說明 |
|------|------|------|
| **簽章演算法** | Ed25519 | 節點和使用者身分簽章 |
| **金鑰交換** | X25519 | X3DH 和 MLS 使用 |
| **雜湊演算法** | Blake3-256 | 256 位輸出，用於 NodeID、content_hash 等 |
| **對稱加密** | ChaCha20-Poly1305 | 訊息加密，256 位金鑰 |
| **Noise 協定** | Noise_XX_25519_ChaChaPoly_BLAKE2s | 節點間通訊 |
| **X3DH 預金鑰數** | 100 | 預生成的一次性預金鑰數量 |
| **MLS 密碼套件** | MLS10_128_HPKEX25519_AES128GCM_SHA256_Ed25519 | MLS 協定密碼套件 |

### 5.2 設計原則
Skynet 協定遵循以下核心設計原則：
1. **效率優先**：在保證基本安全性的前提下，優先考慮系統效能和使用者體驗
2. **現代化方案**：採用經過充分驗證的現代密碼學原語和協定
3. **可擴充設計**：架構設計支援未來安全機制的平滑擴充
4. **實用安全**：提供企業級安全保障，不追求軍規級過度設計

### 5.3 重放攻擊防護
所有加密訊息都包含防重放機制：
- **訊息序號**：每個訊息包含單調遞增的 64 位元無號整數序號
- **重放視窗**：接收方維護最近 1000 個訊息序號的滑動視窗
- **驗證邏輯**：
  1. 如果序號 ≤ 視窗最小值，丟棄
  2. 如果序號在視窗內且已存在，丟棄
  3. 否則接受訊息並更新視窗
- **服務端防護**：維護節點同樣驗證序號，防止惡意客戶端重放訊息

### 6. 資料儲存與同步
子網資料由一組維護節點共同儲存，需保證在部分節點惡性情況下的可靠性與一致性。
- **資料模型**：
  - 所有子網資料以**不可變操作日誌**的形式儲存，每個操作（如添加成員、建立資源、傳送訊息）由發起者簽章，包含單調遞增的序號。
  - 日誌最終收斂為確定性的狀態（可透過重放操作重建）。
  - **資源資料**：包括檔案、圖片等資源的元資料和內容雜湊，資源內容可儲存在分散式儲存（如 IPFS）或本地儲存中。
  - **訊息資料**：包括訊息內容、發送者、接收者、時間戳等，支援端到端加密。
- **複製協定**：
  - 維護節點之間透過 Gossip 協定交換操作日誌，每個節點獨立驗證簽章和權限。
  - 使用**向量時鐘**或**版本向量**檢測衝突，衝突解決規則由子網策略定義（如「管理員操作優先」或「時間戳優先」）。
  - 節點定期對日誌進行雜湊快照，並與其他節點比對，若發現不一致（如節點惡意竄改歷史），其他節點可將其標記為不可信並觸發管理員介入。
- **寫操作**：
  - 客戶端提交寫操作（如邀請成員）到任一服務節點，該節點將請求轉發給所有維護節點。
  - 維護節點驗證權限和簽章後，將操作追加到本地日誌，並廣播給其他維護節點。
  - 客戶端可要求多數維護節點確認後認為操作成功，或採用「寫後讀」驗證：從多個維護節點讀取最新狀態，若不一致則報警。
- **讀操作**：
  - 客戶端可從任意維護節點讀取子網資料，但需從多個節點取得並比較，採用多數一致的結果；或只信任由足夠多節點簽章的資料（如合併簽章）。
  - 為提高效能，客戶端可快取資料並定期輪詢更新。

### 7. 訊息傳遞流程
以使用者 A 向使用者 B 傳送私聊訊息為例：
1. A 的客戶端連接至某服務節點 S（可任意選擇）。
2. 客戶端向 S 發起請求：取得 B 在目標子網內的裝置公鑰清單。S 從該子網的維護節點中取得並回傳（需多個節點比對，或信任由 B 簽章的公鑰包）。
3. A 使用 B 的公鑰執行 X3DH 握手，生成會話金鑰，並加密訊息內容。
4. A 將加密後的訊息包（包含接收者標識：subnet_id、B 的 user_id）傳送給 S。
   - **子網隔離原則**：訊息僅在同一子網內傳遞，不跨子網路由。
5. S 根據 subnet_id 找到該子網的維護節點集合，並將訊息轉發給這些節點（或選擇一個節點儲存離線訊息）。
6. 若 B 線上，其連接的某個服務節點會透過 Gossip 或訂閱機制收到訊息，並推送給 B；若 B 離線，維護節點儲存訊息，等待 B 上線後拉取。
7. B 收到密文後，使用自己的裝置私鑰解密，並傳送確認回執（可選）。

群聊訊息類似，但使用群組對稱金鑰加密，接收者為 channel_id，由維護節點將訊息分發給群內所有線上成員（或儲存為群聊歷史）。

**跨子網轉發**：如需將訊息轉發到其他子網，必須在目標子網中複製該訊息，而非直接引用。複製後，目標子網中的訊息擁有獨立的生命週期。

### 8. 安全考量與惡意假設應對
- **服務節點惡意**：
  - **竄改資料**：所有重要資料（成員清單、公鑰）均有發起者簽章，客戶端可驗證簽章，且從多個節點取得交叉比對。
  - **拒絕服務**：客戶端可切換連接的其他服務節點；子網維護節點若集體作惡，客戶端可透過社交管道發現並重建子網。
  - **竊聽元資料**：端到端加密保護內容，但服務節點仍能看到通訊關係（誰在跟誰聊）。後續可引入 Mix 網路隱藏關係。
- **客戶端惡意**：
  - **濫用資源**：服務節點對每個客戶端實施速率限制，可要求客戶端進行基於難度的工作量證明（如 Hashcash）或支付微額通證（若引入經濟模型）。
  - **假冒身分**：所有客戶端操作需用身分私鑰簽章，服務節點驗證簽章，防止偽造。
  - **女巫攻擊**：加入子網需管理員審核，可防止攻擊者建立大量虛假身分；全域身分註冊可考慮結合外部錨點（如電子郵件驗證）但非強制。
- **子網維護節點共謀**：
  - 若子網中超過半數的維護節點惡意，可竄改資料或拒絕服務。為此，子網建立者可選擇維護節點時要求其提供抵押（如鎖定 Token），或在協定層面允許客戶端從可信第三方取得資料（如社交圖譜驗證）。設計上可引入「見證節點」機制，允許普通節點訂閱子網資料並生成一致性證明，客戶端可依賴這些見證節點。

### 9. 客戶端與服務端互動概要（參考）
客戶端功能參考 IM 產品，主要互動包括：
- **登入**：提供 `auth_id` 和簽章挑戰，取得會話權杖。
- **子網切換**：客戶端列出使用者已加入的子網（本地快取），切換後 UI 顯示對應上下文。
- **聯絡人**：從子網資料中取得使用者清單，支援搜尋。
- **傳送訊息**：端到端加密後傳送至服務節點，服務節點路由到目標子網維護節點。
- **接收訊息**：透過長輪詢或 WebSocket 從服務節點接收推送。
- **群管理**：建立群、邀請成員、修改群資訊，操作需簽章並提交至子網維護節點。
- **資源管理**：上傳、下載、更新、刪除資源，資源內容雜湊儲存在子網資料中，內容可儲存在分散式儲存（如 IPFS 或類似）。
- **檔案傳輸**：檔案作為資源上傳，然後將資源引用作為訊息傳送。

### 10. 協定邊界與免責聲明

Skynet 協定明確定義了以下**不涉及、不負責**的內容：

| 類別 | 說明 | 責任方 |
|------|------|--------|
| **金鑰管理** | 使用者身分私鑰、裝置金鑰的儲存、備份、復原 | 客戶端 |
| **隨機數生成** | CSPRNG（密碼學安全偽隨機數生成器）的實作和熵源 | 客戶端 |
| **金鑰派生** | 從密碼/口令派生金鑰的演算法（如 PBKDF2、Argon2） | 客戶端 |
| **硬體安全模組** | HSM、安全元件（SE）、可信執行環境（TEE）的使用 | 客戶端 |
| **生物辨識認證** | 指紋、臉部辨識等生物辨識方式 | 客戶端 |
| **抗量子密碼學** | 後量子密碼學（PQC）遷移和金鑰封裝機制 | 超綱，暫不涉及 |
| **混合網路** | Loopix 等元資料隱藏技術 | 可選擴充，初始版本不實作 |
| **經濟激勵** | Token、抵押、工作量證明等經濟模型 | 可選擴充 |
| **治理機制** | DAO、投票、仲裁等去中心化治理 | 可選擴充 |

**重要說明**：
- Skynet 協定僅定義網路通訊和資料結構規範
- 客戶端實作者需自行確保上述安全機制的正確實作
- 密碼學安全最終依賴於客戶端的正確實作和使用者的安全意識

### 10. 總結
Skynet 協定透過去中心化服務節點網路、子網隔離、端到端加密和拜占庭容錯資料複製，為建構類似企業 IM 的隱私保護通訊系統提供了基礎。協定設計充分考慮了服務端與客戶端互相不信任的場景，確保使用者資料所有權和控制權掌握在自己手中。

#### 安全定位
Skynet 協定的安全目標是**企業級實用安全**，而非軍規級過度設計：
- ✅ 保護企業通訊隱私和資料安全
- ✅ 抵禦常見網路攻擊和內部威脅
- ✅ 提供良好的效能和使用者體驗
- ❌ 不追求對抗國家級對手的極端安全
- ❌ 不犧牲可用性換取理論上的絕對安全

#### 未來擴充方向
協定設計為未來安全升級預留了擴充空間：
1. **元資料保護**：可引入混合網路技術隱藏通訊關係
2. **後量子遷移**：支援平滑過渡到後量子密碼學演算法
3. **共識增強**：可根據需求升級共識演算法和安全閾值
4. **審計增強**：可擴充更細粒度的安全審計和合規功能
